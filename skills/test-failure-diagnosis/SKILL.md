# 测试失败诊断

## 根因分类

| 类别 | 典型信号 | 建议动作 |
|---|---|---|
| 元素结构变化 | locator timeout、控件找不到 | 局部重录 / 更新稳定 Test ID |
| 缓存失效 | REPLAY_STALE、cache miss 回退 AI | 重新探索刷新缓存 |
| 测试数据污染 | 数据不存在/重复、断言值不符 | 清理数据、独立测试 ID |
| 网络失败 | 请求超时、5xx | 重跑确认是否偶发 |
| 业务断言不满足 | 预期与实际不一致 | 确认是缺陷还是预期过期 |
| 等待条件不代表业务结果 | 操作成功，但通用浮层未隐藏；列表还在展示旧结果 | 等待业务结果就绪；按字段区分相关浮层和无关浮层 |
| 环境问题 | 页面打不开、登录失败、许可证显示已过期 | 检查目标环境地址、账号和许可证；把环境证据与脚本断言分开说明 |
| 用例整体超时 | 报告 attempt.error 为 TEST_TIMEOUT，当前步骤可能同时显示 This operation was aborted | 检查整条用例耗时与执行预算。优先用 Skill 中已验证的定位执行可确定的交互。 |

## 诊断步骤

1. 定位首次失败的业务步骤及具体操作。回归运行的失败位置变化时，分别写明原障碍是否已越过、现在失败在何处；只有完整用例通过才验证了修复。
2. 用失败时的页面快照或 Trace 判断当前停在登录页、列表、外层弹窗、画布还是抽屉。先确认实际存在的控件再生成操作；通知和带确认按钮的对话框需要分别辨识。元素此前出现、一次操作后消失时，先检查该操作是否离开了所需页面，再调整定位。优先采用业务 Skill 中已验证的操作。
3. 区分触发动作、界面反馈和最终结果。例如筛选标签出现只说明条件已提交，浮层是否消失也不能证明列表已刷新；旧列表中的零匹配不能作为新增前的缺失证明。检查新结果或明确空态后再评价业务断言。
4. 对比保存前、预期、实际配置差异。根据证据给出根因候选与修复建议，区分已证实与待核查项。修复不得修改业务预期或跳过写入前的数据保护检查。

## 输出要求

- 面向业务人员的失败描述：失败的步骤 + 预期与实际 + 根因候选 + 建议操作。
